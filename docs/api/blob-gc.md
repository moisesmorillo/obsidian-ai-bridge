# Blob garbage collection API

The verified owner uses `GET /owner/blob-gc` to see a dry run and current collection state. The route uses Cloudflare Access, the configured service origin, and `Cache-Control: no-store`. The console lists the number of reclaimable blob objects and their combined byte size before it offers a confirmation form.

The owner submits `POST /owner/blob-gc` to confirm or continue collection. The route requires the same-origin `Origin` header, a browser-bound one-use CSRF token, and verified owner Access. Each request starts or advances one bounded batch. Durable Object alarms continue a confirmed run until it reaches the idle phase.

Collection lists only canonical `blobs/<sha256>` keys in the existing R2 bucket. It never lists or deletes `backups/` objects. SQLite marks each candidate only after it checks current files, every retained revision, and active packed-export blob sources in a transaction. `blob_refs` alone does not establish reachability or inventory all R2 objects.

The owner page shows the current phase, marked object count, marked bytes, delete state, and typed storage-failure state. The API reports `delete_state` as `idle`, `active`, or `unknown`. A durable SQLite claim prevents a second owner or alarm call from deleting the same batch. The claim stays set until its R2 request settles. A successful delete clears its exact marks and claim in one transaction. A settled delete error releases the claim but keeps every batch mark for a later retry, even when R2 deleted only part of the batch. A successful retry clears its marks, claim, and prior error in one SQLite transaction.

When a Durable Object starts with a persisted active claim, it changes the state to `unknown`. This state means the system lacks proof that the R2 request settled. The claim has no timeout. The marks and publication fence stay in place, and an owner retry cannot clear the claim. Recovery needs R2 settlement proof or conditional-delete fencing. OAB-41 tracks this trigger-based recovery work. A mark or generation change between blob HEAD evidence and the final publish transaction returns HTTP 503 with `blob_gc_in_progress` and `retry_after_seconds: 1`.

Preview does not change marks. The confirmed run rechecks every candidate in SQLite before marking it. Each inventory call reads one page. Each SQLite and R2 operation handles at most 100 hashes. One preview reads at most 32 R2 pages; a larger inventory returns an unavailable response and does not start deletion. Confirmed runs persist the R2 cursor and continue in later bounded batches. Each inventory page applies only when its saved run identity, phase, and cursor still match. SQLite applies reachability marks and cursor advancement in one transaction. Reachability queries select distinct hashes, so returned reference rows stay within the candidate count.
