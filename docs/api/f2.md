# F2 local API

This document describes the F2 routes and behavior implemented by the local Worker. It does not claim deployed Access policy, external client success, plugin behavior, device state, or preserved plugin queues. OAB-7.7 and OAB-7.8 retain those checks.

## Service and local test setup

The service uses one configured HTTPS origin. OAuth issuer, resource metadata, consent redirects, and API authority use that origin. A request `Host` value does not select the origin or vault.

Set these Worker bindings for local F2 work:

| Binding | Meaning | Synthetic local value |
| --- | --- | --- |
| `SERVICE_ORIGIN` | Canonical HTTPS service origin | `https://service.test` |
| `ACCESS_TEAM_DOMAIN` | Access issuer base domain | `https://team.test` |
| `ACCESS_AUDIENCE` | Access application audience | `synthetic-access-app` |
| `OWNER_SUBJECT` | Configured owner subject | `synthetic-owner` |
| `OAUTH_KV` | Local OAuth provider state and token storage | Local KV binding in `wrangler.f2.jsonc` |
| `VAULTS` | SQLite Durable Object authority | Local `Vault` Durable Object binding |
| `R2_BUCKET` | Blob storage for the Worker | Local R2 bucket binding in `wrangler.f2.jsonc` |

All four auth settings must pass configuration validation. Missing or invalid auth settings deny local OAuth and owner behavior. Access uses an RS256 assertion whose issuer, audience, and subject match the configured values. The Worker fetches keys only from the configured team domain. Tests sign assertions with synthetic keys and mock that key response. Never copy test values, credentials, or identifiers into a deployed environment.

Run the local F2 suite from the repository root:

```sh
cd apps/worker && bunx vitest run --config vitest.f2.config.ts
```

Run documentation validation and the complete local project check from the repository root:

```sh
bun run docs:check
bun run check
```

`bun run check` includes lint, documentation validation, type checks, tests, and a Wrangler dry-run build. It does not authorize or perform deployment.

## OAuth and discovery

All OAuth routes use the canonical service origin. Authorization uses OAuth 2.1 authorization code with PKCE S256. The provider accepts dynamic public-client registration and configured pre-registered public clients. It accepts authorization-code and refresh-token grants only. Token exchange and client-credentials grants are disabled. Access tokens expire after one hour. Refresh tokens expire after 30 days and rotate on use.

| Method and path | Behavior |
| --- | --- |
| `GET /.well-known/oauth-authorization-server` | Authorization server metadata, including implemented authorization, token, registration, grant, and scope capabilities. |
| `GET /.well-known/oauth-protected-resource` | Resource metadata for the canonical origin. The resource is the origin, not `/mcp`. |
| `POST /oauth/register` | Dynamic public-client registration. The client must use authorization code and refresh grants with `code` responses. |
| `GET /authorize` | Access-protected consent display. Requires one valid S256 challenge and known scopes. Shows client, redirect URI, and requested scopes. |
| `POST /authorize/consent` | Access-protected, browser-cookie-bound one-use approval or denial. Approval records the durable consent generation before issuing a code. |
| `POST /oauth/token` | Provider token exchange and refresh. The client must use the registered redirect URI and PKCE verifier for code exchange. |
| `GET /owner/clients` | Access-protected client list and owner actions. |
| `GET /owner/clients/:clientId/grants` | Access-protected paged grant status, including pending provider cleanup. |
| `POST /owner/clients/:clientId/rename` | Access-protected rename using owner CSRF state. |
| `POST /owner/clients/:clientId/revoke` | Access-protected durable client revocation using owner CSRF state. |

Owner POST routes require a valid Access assertion, the browser-bound CSRF value, and the canonical service origin. Revocation writes authoritative denial in the Durable Object before provider KV cleanup. One owner revocation request spends from a shared 48-operation budget across its CSRF Durable Object RPC, denial registry RPC, provider KV list and delete calls, and cleanup-completion registry RPCs. Cleanup lists at most one token key at a time, deletes one token per step, and deletes the grant only after a token-prefix list returns no keys. A failed or incomplete cleanup leaves pending owner state. The next API or refresh request still checks the Durable Object and is denied. A new owner consent generation may reconnect the client. Old authorization codes and refresh tokens cannot restore an older generation.

## Permissions and failures

Scopes are `vault:read`, `vault:write`, and `vault:delete`. Each REST route and MCP tool checks its required scope at the Worker boundary, then the Durable Object checks scope and revocation before data access or mutation. `vault:write` does not grant read or delete. Authorized tool results include the operation-authorized `epoch`. Identity, scope, and revocation denials return HTTP `401` or `403` without an epoch or note content.

OAuth and owner failures use safe text or redirects and do not expose tokens, assertions, or note bodies. REST errors use `{error, message, ...details}`. MCP failures use a structured result with `epoch`, `code`, and safe `message` only after operation authority permits the epoch. Input shape errors that occur after identity and authority checks retain the authorized epoch. Unknown infrastructure failures do not expose exception text.

## REST routes

REST requests use `Authorization: Bearer <access-token>`. JSON responses use the implemented contracts in `docs/spec.md` section 6. Mutations require their exact observed ETag, create-only predicate, and/or observed epoch. Successful mutation responses return an ETag and publication sequence. An ETag has the quoted form `"<epoch>.<revision>"`.

| Method and path | Scope | Contract |
| --- | --- | --- |
| `GET /v1/vault` | `vault:read` | Current epoch, head sequence, counts, limits, capacity, and attention state. |
| `GET /v1/manifest?page=<token>` | `vault:read` | Bounded metadata page with epoch-bound ETags and a continuation token. Includes tombstones. |
| `GET /v1/changes?epoch=<epoch>&since=<seq>&limit=<n>` | `vault:read` | Bounded immutable feed page. A stale epoch returns `409 epoch_mismatch`. |
| `GET /v1/files/*path` | `vault:read` | Current file content and metadata. `rev`, `Range`, and text `offset`/`length` select bounded content where supported. Responses carry `ETag`. |
| `PUT /v1/files/*path` | `vault:write` | Create with `If-None-Match: *` or update with exact `If-Match`, plus `X-Vault-Epoch`. Raw request bytes form the content. |
| `DELETE /v1/files/*path` | `vault:delete` | Conditional tombstone creation with exact `If-Match`. |
| `POST /v1/files/*path:rename` | `vault:write` | JSON `{to}` and exact source `If-Match`. Destination collisions do not overwrite. |
| `POST /v1/files/*path:append` | `vault:write` | Raw text append. Requires `Idempotency-Key` and `X-Vault-Epoch`. Missing key returns `428 idempotency_key_required` after identity and authority checks. |
| `POST /v1/files/*path:restore` | `vault:write` | JSON `{source_rev, as_conflict_copy?}` and exact current destination `If-Match`. |
| `GET /v1/history/*path?page=<token>` | `vault:read` | Bounded content-free revision history. |
| `GET /v1/search?q=<query>&limit=<n>` | `vault:read` | Literal bounded text search with coverage counts. |

REST `precondition_failed` returns the authorized current ETag, hash, and deletion state. It includes current text only for an identity with read scope. Tombstones preserve path history. Create-only can recreate an exact tombstoned path without deleting the old revision. Append rejects tombstones. Restore requires the exact source and current destination observations. A write does not grant read or delete.

Relevant status families include `401 revoked`, `403 forbidden_scope`, `409 epoch_mismatch` or collision, `412 precondition_failed`, `413` size refusal, `428 idempotency_key_required`, `429 admission_limited`, `503` temporary storage/authority failure, and `507 capacity_exceeded`. See section 6.2 of `docs/spec.md` for the canonical complete error list and response details.

## MCP Streamable HTTP

MCP uses `POST /mcp` with a bearer token, `Content-Type: application/json`, and `Accept` containing both `application/json` and `text/event-stream`. The service supports stateless JSON responses. A supplied `Origin` must match the canonical service origin. MCP discovery and tool calls use the same OAuth and Durable Object authority as REST.

Every authorized structured tool outcome carries the operation-authorized epoch. Unauthorized identity, scope, or revocation returns HTTP `401` or `403`, without epoch or content. MCP input schemas are strict. Extra fields fail validation.

| Tool | Scope | Arguments | Result |
| --- | --- | --- | --- |
| `list_notes` | `vault:read` | Optional `prefix`, `include_large` | Epoch and at most 256 `{path, etag, size, updated_at, large}` entries. |
| `read_note` | `vault:read` | `path`, optional `etag`, `offset`, `length` | Epoch, path, ETag, optional content, and `truncated`. A stale supplied ETag returns current ETag without content. Offsets and lengths use UTF-16 code units. |
| `search_notes` | `vault:read` | `query`, optional `limit` | Epoch, bounded search hits, indexed Markdown count, and unindexed large Markdown count. |
| `get_history` | `vault:read` | `path` | Epoch and at most 256 content-free revision entries. |
| `create_note` | `vault:write` | `path`, `content`, `epoch`, optional `idempotency_key` | Epoch and new ETag. Create-only. |
| `update_note` | `vault:write` | `path`, `content`, exact `etag`, optional `idempotency_key` | Epoch and new ETag. Stale ETag returns authorized current conflict metadata. |
| `append_to_note` | `vault:write` | `path`, `text`, `epoch`, required `idempotency_key` | Epoch and new ETag. Refuses tombstones and stale epochs. |
| `delete_note` | `vault:delete` | `path`, exact `etag` | Epoch and tombstone ETag. |
| `restore_note` | `vault:write` | `path`, `source_etag`, `current_etag`, optional `as_conflict_copy` | Epoch and new ETag, using the exact source and current ETags. |

`create_note` and `append_to_note` carry an explicit epoch because they do not carry an ETag. Append keys are opaque strings of 8 to 128 characters. Missing or absent append keys return HTTP `428` only after identity, scope, and Durable Object authority checks. A supplied invalid key remains an input error. MCP and REST use the same operation authority, mutation receipts, and history rules.

## Response and admission bounds

The MCP request envelope limit is 6,100,000 wire bytes. The Worker checks declared and streamed sizes before decoding, then scans the decoded source before `JSON.parse`. The scan limits nesting to 64, containers to 65,536, total comma separators to 65,536, string tokens to 65,536, and separators within one container to 16,384. This whole-envelope gate includes unused fields and metadata. It checks structural work only. The MCP SDK and canonical Zod schemas own semantic protocol shapes. Complexity refusal returns HTTP `413 request_too_complex`.

One isolate-wide MCP envelope slot is acquired before body demand and held through response production and cleanup. A competing MCP request receives `429` and `Retry-After: 1` before it reads the body. MCP read tools also use the four shared authoritative read slots used by REST.

The 65,536-byte response chunk bound applies to each encoded or delivered chunk, not the entire response. A response may contain many bounded chunks. Producer EOF or cancellation cleanup releases local ownership after started work and cleanup settle. This does not prove client receipt or native resource release.

The MCP list estimate starts with one 128-byte base allowance. It then adds each entry's UTF-8 JSON bytes and one comma byte between entries. The estimate cap is 65,536 bytes and covers list entries, not the complete JSON-RPC frame. It is an estimate, not the frame's exact encoded size. The separate 1,000,000-byte metadata estimate ceiling is not the list estimate or the frame size. Exceeding a result limit returns an explicit error, not partial success.

Static MCP source accounting allows at most 6.1 MB of request bytes, 12.2 MB of decoded UTF-16 source, and 12.2 MB of parsed string payload by source-character count. A returned note can add up to 2 MB of UTF-16 content. The scanner also bounds containers, separators, strings, and nesting. SDK validation may copy parsed structures or strings. Engine object overhead, native string representation, SDK copies, response objects, and combined isolate heap use are not measured or statically bounded in bytes. REST read and mutation owners can also run concurrently within their separate four-slot limits. These source limits do not prove a combined heap peak below 128 MB.

The Worker does not materialize the full vault or one complete escaped note result for MCP list and note responses. Full response-size claims do not follow from bounded chunks. Slow consumers keep operation ownership until producer completion or cancellation cleanup. Uncertain authority outcomes retain their original durable admission deadline. Permanently blocked work can exhaust bounded slots and cause safe refusal.
