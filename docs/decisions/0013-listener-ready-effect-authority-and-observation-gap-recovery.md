# ADR 0013 — Listener-ready effect authority and observation-gap recovery

## Status

**Accepted and implemented in merged corrective M4 PR #55.** This record supersedes only ADR 0009's implication that retaining exact effect evidence and successor ranges is sufficient across an unobserved listener interval. ADR 0009 remains the historical account of the v4 format, history ledger, and conservative treatment of *observed* events. ADR 0012's archive namespace and frozen receipts are unchanged. Its bounded disposable Obsidian 1.13.7 evidence is recorded in the listener-gap qualification; M5's broader, separately bounded qualification is recorded in the [M5 final report](../qualification/m5-final.md).

## Context

On a large vault, attaching Vault listeners before layout readiness amplifies the host renderer's pre-layout work and fails at 5,000 paths. Delaying attachment removes that amplification but leaves a real interval in which M4 cannot prove the absence of local successor events. Merely moving `events.attach()` would let queued or resumed work dispatch or release reservations on silence. Exact local postcondition, remote revision, receipt, or equal numeric listener epochs proves an effect/current sample, **not continuous event coverage**. `successor-review-required` requires an *observed* successor range and must not be entered by fabricating an event. Existing `evidence-required` and `blocked` describe other failure/attention states, not this missing observation proof. Current strict v4 cannot express the gap.

## Decision

### Representation and compatibility

| Criterion | A: `observation-gap-review-required` operation phase | B: orthogonal `observationCoverage` fence |
| --- | --- | --- |
| Ordinary queued or restored operation | Replaces its real admitted/restored phase; needs another durable saved phase to resume honestly | Retains its phase and restore linkage independently |
| Final confirmed history step (`nextStepIndex: null`) | Must encode a synthetic active phase despite a completed step; completion and reservation policy become ambiguous | Keeps step/receipt truth; fences finalization before terminal commit |
| Unknown/potentially dispatched effect | Phase cannot say whether exact recovery is still required without inspecting separate fields; resumption risks redispatch | Keeps effect certainty and exact recovery path independent of coverage |
| Scope | One apparent phase but many cross-product exceptions in both history and non-history machines | One closed operation-level predicate across both machines |

**Select B.** Add a required closed v5 operation field `observationCoverage: continuous | gap-review-required` on *every* v5 operation, both history and non-history. It is not a global epoch or a replacement for existing phase, local/remote effect certainty, history progress, preservation receipts, successor ranges, or review links. `continuous` means only that no *known uncovered interval relevant to this active operation* remains; it never establishes historical causal provenance. `gap-review-required` retains all exact evidence and reservations and denies new effect dispatch, silence-based completion, terminalization, and reservation release. Exact recovery/settlement of an **already dispatched** effect may continue when its required read capability is available, including a confirmed final history receipt, but may not clear this fence by itself. Closing Fetch on detach forbids new recovery requests while detached; later read-only exact recovery is not a new mutation dispatch. Even a prepared effect whose host call cannot be proved absent must use the existing unknown-effect recovery rules; no automatic repeat. Existing observed successor evidence remains observed and is never cleared or synthesized by the gap fence. A terminal operation committed before the gap stays terminal; a final step confirmed but not atomically terminal before the gap is active, reserved, and fenced even with `nextStepIndex: null`. No-op history decisions already atomically completed before the gap are terminal.

Neither A nor B fits strict v4. **Device state must become v5.** Freeze the exact v4 decoder (as v2/v3 already are); do not broaden its enum, append an optional v4 field, or reinterpret old records. v4→v5 is strict decode and validation, deterministic projection of all M3/M4 fields, exact reviews, operations, phases, receipts, history steps, reservations, effect certainty, successor ranges and links, followed by v5 complete validation, bounded encoding, same-key write, exact read-back and strict v5 decode **before publication or effectful resume**. Project `continuous` only for already-terminal operations; project `gap-review-required` for every nonterminal v4 operation (including blocked, evidence-required, restored-pending-review and refined/legacy history). This is a cold-start migration with no assumed coverage, regardless of saved listener epoch. v2/v3 retain their frozen decoding and existing sequential projections into v4; the final v4→v5 fence applies before any v5 runtime publication. No historical effect, successor range, history choice or proof is invented. Validate capacity on the full prospective encoded state and fail closed on size/quota/save/read-back/integrity failure; do not truncate records to fit. Keep the existing bounded collection ceilings and enforce the tested 13 MiB v5 serialized-state limit, which accommodates maximum-cardinality valid v4 projections plus gap-authority overhead. Failed write/read-back is unavailable; an exactly committed v5 write is recognized on next startup. There is no reverse migration; old strict v4 rejects v5 as unsupported. Historical rollback of valid older bytes cannot be proved absent: recover conservatively and require operator reconciliation. The structural `MirrorRuntimeOwner` version **and** same-realm coordinator/registry version must become **5** in the same atomic compatibility change; no v5 writer with a v4 owner, and no v5 owner advertised with an incomplete lease/classification/transfer surface. Existing v4 owner cannot be reused in the same App realm: fail closed and require host restart, not an unsafe fallback. No Worker API or handoff wire-format change.

### Lifecycle and dispatch authority

`MirrorRuntimeOwner` owns one process-local observation/effect dispatch lease; `MirrorObservationEpochCoordinator` is its sole listener/layout readiness authority. This lease is **not durable** and its numeric epoch is not continuity evidence across process death. Only the owner publishes a lease after *all* Vault event refs have attached and layout readiness is established. Every new M4 local preservation/create/replace, remote mutation, and history-step remote mutation must check that lease **immediately before crossing the host/Fetch dispatch boundary**, after durable preparation and immediately before the actual call. That synchronous gate also checks the exact durable effect phase/certainty; history effects require the current `nextStepIndex` step identity and its matching phase. Blocked, evidence-required, terminal, and non-current-step operations cannot dispatch. Scheduler admission, earlier checks, or a captured boolean are insufficient. Serializing lease invalidation with the final synchronous dispatch gate must make detach-vs-dispatch linearizable; queued work that reaches the gate afterward cannot call the host or Fetch. The same gate must protect new M3 effects as applicable; M3 deletion remains event-only and gap scans positive-only. If a durable prepared state is saved but the call was not made, retain it for exact recovery; only an explicit certainty proof that dispatch never happened may allow a new attempt after review. Do not treat Abort as rollback.

**Cold startup:** load/strictly migrate state → configure connection **without effectful resume** → wait for layout readiness → attach **all** Vault listeners → mark the new observation epoch → durably classify persisted gap-sensitive operations before publishing the effect lease (v5 cold restart fences every active operation that is not already gap-fenced, including records previously marked continuous) → publish the listener/configuration lease → run positive bootstrap → durably drain queued observations → activate normal event delivery and scheduling → resume eligible persisted M4 work. Callbacks arriving between attachment and classification are queued, then persisted as **real observed** events in the fresh epoch; they cannot trigger work against unclassified state. Buffer overflow, listener-registration failure, or drain failure synchronously keeps or revokes the attachment's one-shot effect lease and prevents normal scheduling; no same-attachment retry may restore authority. Classification must commit before any effectful resume, review/release or M3 job against reserved paths. If classification cannot persist, keep admission closed and state unavailable; do not attach early to avoid the fence. Positive bootstrap is the bounded startup exception and remains positive-only: before the event drain, only current-scan `dirtyPresent` paths without unresolved M3 intent or M4 reservations may use the scheduler; persisted delete/rename cleanup and uncertain M3 work wait for normal readiness. Concurrent readiness callers, including settings reapplication, share one single-flight drain/activation barrier; no caller may mark normal scheduling ready until that captured listener session's drain commits. A stale barrier cannot activate a replacement session. The startup-only v3 postcondition recovery can still read and settle exact evidence without writer/remote dispatch, but cannot grant continuity.

**Detach:** synchronously invalidate lease **first** → prohibit new effect dispatch → close new Fetch admission → detach Plugin event refs → allow already-dispatched effects to settle (or defer exact recovery until read-only Fetch admission is available again) → prohibit reservation release for any active operation spanning lost coverage. After synchronous invalidation and listener removal, run a serialized durable classification barrier; detach itself need not await disk I/O, but until that save commits a process-local release fence keeps all affected reservations and new work blocked. Do not report the session as safe for re-enable or clear that fence before commitment. If persistence fails, same-realm re-enable fails closed until durable classification succeeds; process death invokes the cold-start fence. No waiting for network completion before invalidation. UI/timers/commands may detach afterward. No callback after event-ref removal is treated as continuity. After normal delivery is active, any event-sink rejection is also treated as lost observation: stop further callback admission, synchronously invalidate the dispatch lease and close Fetch/scheduling gates, then attempt serialized durable gap classification. Failure of that save cannot restore the process-local lease; only a later classified listener epoch may publish new authority.

**Reattach:** wait layout-ready → attach all listeners → establish fresh observation epoch → durably classify gap-spanning active operations before publishing the new effect lease → publish the lease → run positive-only bootstrap → durably drain buffered observations → activate normal delivery/scheduling → permit fresh linked reviews and eligible persisted-work resume. Every review/release remains serialized and revalidated by the state owner. An existing same-realm owner can settle already-dispatched requests meanwhile, but cannot release their paths. Reattached listeners cannot retroactively supply missing events. Connection creation/configuration must not call `resumePersisted()` or otherwise start M4 until classification succeeds.

The durable classification is owned by a single core gap-transition policy invoked through a serialized `MirrorStateOwner` barrier by `MirrorRuntimeOwner`; the barrier also waits for earlier queued transitions when no operation currently appears to need fencing, without rewriting an unchanged state. A delayed admission or effect-settlement save therefore cannot publish a continuous operation after classification. Neither action services nor plugin event handlers independently decide which phases to fence. Fence every nonterminal operation that might have spanned an uncovered interval, even if currently queued, blocked, or remote-only. An active operation admitted *after* the new ready epoch and proven not to span a gap starts `continuous`. Already-terminal records are immutable audit evidence. A state-owner save racing effect settlement merges exact evidence and fence atomically, never replaces an updated effect with an older snapshot. In particular, when a final history tombstone response arrives after lease invalidation but before its receipt save, commit its exact ACK/step receipt and deferred-state clearing with a **nonterminal fenced parent** and `nextStepIndex=null`; do not reuse v4's atomic receipt-plus-terminal branch. If the terminal save committed before invalidation, it stays terminal. This ordering is serialized against detach, so neither branch can release on uncovered silence. If process death occurs before same-realm fence persistence, cold-start blanket classification is mandatory before effectful resume.

### Fresh review and ownership transfer

A fence is **not** a successor event. `ReviewedReconciliationRuntime` serializes a queue barrier for callbacks since reattach, then requests a **new** complete read-only review through `ReconciliationReviewService` for the entire predecessor reservation set (including history group), current local presence/identity/hash, ACK/M3 work, remote revision/receipt/recovery evidence, configuration and runtime identity. Review creation must explicitly accept a linked gap predecessor without pretending it has a successor range. For history, the review path set is the predecessor's exact bounded reservation set, **not** rediscovery from current deferred edges (the final confirmed step may have cleared them). Current deferred edges, if any, are separately rederived and checked for conflicts; no old mapping is reconstructed. Admission rechecks all snapshots under `MirrorStateOwner`. Refresh/epoch/configuration/group change, unstable/unknown local evidence, incomplete remote inventory, unavailable remote or recovery evidence, or unresolved effect certainty keeps the predecessor active/reserved with its gap fence. A missing/renamed path is current evidence, not a fabricated delete/rename event; absence never authorizes M3 deletion. A review cannot overwrite exact receipts or repair older historical artifacts. Existing real successor ranges must also satisfy ADR 0009's successor review rules; gap settlement does not consume or erase them without a complete review.

Transfer rules, in this order, in **one** serialized state save (save failure leaves old reservation/fence):

1. Settle or recover any already-dispatched effect with exact operation/step receipt or postcondition first. Unknown/potentially dispatched effects with no conclusive exact outcome **cannot** be declared absent, retried, or bypassed by a fresh matching hash/revision; keep reserved for existing recovery/attention. A confirmed effect is retained as fact, not authority over later changes.
2. A no-effect settlement persists a completed predecessor-linked v5 gap-group review (without a fabricated child operation) and is allowed only if a fresh complete snapshot proves *every reserved path* currently aligned with the established ACK and exact remote/local state, there is no unresolved M3 work, no unknown effect, no deferred-history blocker left by this predecessor, and all preservation/step evidence required for **effects already performed** is exact (unused prepared receipts are retained as historical preparation, not invented as verified archives). For a refined history plan, every step must have its exact confirmed tombstone receipt, `nextStepIndex=null`, and its selected deferred blockers must already have been cleared by exact step settlement; any pending step or changed group disallows no-op. For an ordinary restored-pending-review operation, retain ADR 0009's requirement for a linked ordinary reviewed successor: alignment alone does not release its restore fence. No-op records fresh review linkage, marks it and predecessor terminal and releases reservations atomically without dispatch. It is never based only on matching bytes, unchanged remote revision, or epoch equality. If a completed final history step's *finalization* was withheld by the gap, this rule provides its truthful terminal path after its exact receipt and group/ACK/deferred-state checks.
3. Otherwise, only permissible **ordinary reviewed actions** (or one explicit newly reviewed bounded history decision when current deferred edges still form a complete eligible group) may take over the predecessor's reservation set. A one-path predecessor takes one ordinary reviewed successor. A multi-path history predecessor uses a **single atomic gap-transfer batch**: one fresh complete **gap-group** review of the exact reserved set plus a separately admitted ordinary target-scoped review/action pair for each currently non-aligned path. Each ordinary pair retains its existing exact snapshot-to-operation/reservation equality (no shared multi-path reservation on every child); the gap-group review binds the common complete evidence, current owner identity and the exact set/identity of the child reviews. V5 gives this review a dedicated predecessor-linked durable review variant (not a fake 1:1 operation review): it records its review ID, complete content-free snapshot, predecessor ID and completed/stale status; each child retains its ordinary 1:1 review-operation pairing. No body is persisted. Aligned paths need no successor effect and are released only in that same batch save. Revalidate all reviews and each action, cross-path effects, capacity, and overlaps together; install every successor reservation, link all successor IDs to the predecessor, complete old review/predecessor, and release only aligned paths in one save. Retain the old v4 `successorOperationId` for its existing restore/observed-successor meaning; v5 adds a bounded `gapSuccessorOperationIds` list for gap transfer (one ID for a one-path transfer, multiple for a batch, empty on no-effect settlement). V5 validates these as a distinct link kind with a real gap-group review, **not** against the v4 observed-successor-range prerequisite. No partial batch commit or action on only the easy path. Each ordinary successor acts on its own reviewed target with its existing action contract; this is **not** a new multi-path mutation capability. Each decision is derived from **current** evidence, not guessed missing events or stale original authority. A pending old history step is not resumed under old authority after a gap; unknown dispatched steps must resolve first. If current deferred edges require a new history choice, use a fresh complete bounded history admission for exactly the reserved group; a changed/incomplete group blocks transfer rather than dropping a reservation. `defer` cannot release reservations. If any path has no safe permitted reviewed action (including absent/renamed path), group evidence is incomplete, or the required batch exceeds state/operation capacity, hold the *whole* predecessor for explicit attention/new evidence; never invent deletion authority. For a fully completed final history step, this gives either exact no-effect settlement on complete alignment or an ordinary per-path reviewed batch on changed evidence, without inventing another cleanup step.

After a successful transfer, the new operation carries fresh continuous coverage only if its review/admission and dispatch occur in the current ready epoch and its immediate dispatch lease remains valid; otherwise fence it too. Admission can never have two active operations owning a path; the atomic old-terminal/new-active swap is the sole transfer exception. Queue-barrier/serialized save protects events arriving during review/commit: they invalidate the snapshot or are sequenced into the new owner's observed successor evidence; no event is silently lost. The old operation never resumes a new effect after transfer. Terminality/release must not be inferred merely because a history `nextStepIndex` is null.

### Transition matrix

Legend: `G` = durable gap-review-required; `C` = continuous only after fresh ready-epoch admission/transfer; `N` = new effect dispatch; `R` = reservation release; `V` = fresh complete linked review. For all active rows below, `G`, `N=no`, `R=no`, `V=yes` until the above atomic settlement/transfer; existing exact evidence is preserved. `T` means no-effect terminal **only** under rule 2; `X` means rule-3 reviewed atomic transfer; `H` means held until exact effect recovery, then T/X. These outcomes are not automatic consequences of a matching hash.

| Situation at gap boundary | Retained phase/effect/history truth | Fence; N/R/V | Exact terminal route |
| --- | --- | --- | --- |
| 1. Queued; none dispatched | admitted, not-dispatched, full reservations | G; no/no/yes | T if fully aligned and permitted, else X; never resume old action |
| 2. Preservation prepared, no proven call | preserving, pending receipt/prepared local effect | G; no/no/yes | H if dispatch uncertainty, else review T/X with unused preparation retained; never assume not-dispatched from phase |
| 3. Local call dispatched, postcondition unknown | mutating-local, effect ID/expected hash, unknown certainty | G; no/no/yes | H; exact postcondition recovery first, no redispatch |
| 4. Local effect confirmed | confirmed synthetic effect/postcondition and any observed successor range | G; no/no/yes | T if fully aligned/no remaining effect, else X; real successor rules also apply |
| 5. Remote-only effect pending | mutating-remote or prepared; not-required local observation and remote certainty | G; no/no/yes | H for potentially dispatched call; otherwise T/X after review |
| 6. Remote-only effect confirmed | exact remote receipt/revision, no local-effect claim | G; no/no/yes | T on full alignment else X; no old-effect redispatch |
| 7. History step pending | parent phase and ordered step index/step pending, full group reservations | G; no/no/yes | X for freshly reviewed history choice or safe ordinary action; T only with no uncleared blockers, never continue old step |
| 8. History preservation confirmed | step-scoped exact verified archive receipt; step still pending/ready | G; no/no/yes | X after fresh review; receipt retained, no new old-step dispatch |
| 9. History remote mutation unknown | current step mutating/evidence-required; step UUID and exact uncertainty | G; no/no/yes | H via exact step-ID receipt recovery, then review T/X; never repeat tombstone |
| 10. Final history tombstone confirmed, final commit withheld | exact final step receipt, all steps completed, `nextStepIndex=null`, parent not terminal | G; no/no/yes | T only after full aligned group/deferred-clear proof; else X or hold; no second tombstone |
| 11. Process death in any row 1–10 | persist exact last committed phase/effects/steps; in-flight outcome may be unknown | On reload G; no/no/yes | Cold classification before resume; follow same row, recovering exact effects first; even prior C is not continuity |
| 12. Reattach, aligned evidence | retain row-specific phase/effects/receipts and observed ranges | G; no/no/yes | T only if rule 2 holds; restored parent requires X; unknown effect H |
| 13. Reattach, changed local evidence | retain exact old effect truth plus new sampled identity; no synthetic range | G; no/no/yes | X if current reviewed action is permitted after H; otherwise hold; no silent overwrite |
| 14. Reattach, changed remote evidence | retain old receipt/revision and sample new remote truth | G; no/no/yes | X only on newly permitted conditional review after H; otherwise hold; never overwrite latest |
| 15. Reattach, absent/renamed path | retain predecessor and full original reservations; sample absence/current bounded group | G; no/no/yes | X only for current policy-permitted explicit action after H, else hold; no inferred successor/delete |

A terminal operation committed *before* detach/death is not retroactively fenced, even if its audit record retains reservations as historical fields: its release already occurred under the pre-gap queue barrier. For a crash in the narrow window after an external call and before receipt persistence, classify effect certainty conservatively as potentially dispatched and use only exact postcondition/operation-ID recovery, not a fresh dispatch. If the host cannot establish that outcome, the record remains reserved. These rules apply equally when the process exits without a detach callback.

## Consequences

This compatibility/runtime correction was not by itself an M5 readiness claim. M5 later completed a separate A1–A12 qualification; M6 is now NEXT for planning. The implementation lands the v5 state/owner compatibility change atomically with dispatch fencing, startup ordering, gap review/transfer, validation, and tests. Focused tests cover migration and downgrade, process-death/listener-gap classification, same-text successor events, final history settlement, save failures, dispatch-lease invalidation, review transfer, startup buffering/readiness, and artifact/runtime boundaries. The bounded disposable-host result is recorded in [M4 listener-gap qualification](../qualification/m4-listener-gap-recovery.md).

**Implemented ownership:** core state constants/types/validation and migration own the v5 coverage and predecessor-linked gap-review schema; `ReconciliationReviewService` plus the serialized `MirrorStateOwner` own complete-group review and atomic transfer; `ReconciliationEffectExecutor` and the history resolver preserve exact effect certainty; plugin state codecs keep v2/v3/v4 frozen and perform v5 same-key migration; `MirrorRuntimeOwner`, `MirrorObservationEpochCoordinator`, `ReconciliationRuntimeOwner`, and the Fetch/local dispatch adapters order startup, lease checks, and normal scheduling. The review policy is not duplicated in action services. Tests cover the core state/review matrix, plugin migration/runtime/event/UI boundaries, and packaged artifact behavior.

The observed implementation changes 44 production files with 6,343 additions and 305 deletions (net +6,038) under `apps/obsidian-plugin/src/` and `packages/core/src/` (unified-diff counts; tests and documentation excluded). It exceeds both the ten-file and 1,500-net-line guidelines. The frozen v4 compatibility codec accounts for 2,204 new lines; the remaining changes implement the inseparable v5 migration, owner/registry transition, dispatch lease, current-scan positive-only startup scheduling and event barrier, gap classification, and complete-group recovery/transfer. Each new bootstrap inventory clears prior-scan positive markers before admitting current positives; event persistence failure revokes the lease, and exact effect dispatch also requires current durable mutation admission. These checks are required to keep the pre-barrier projection scoped to fresh observations and fail closed across reattachment. Splitting an activated slice would leave either a v5 writer/runtime mismatch or operations fenced without the required review/recovery path. This is the authorized atomic corrective exception to both size guidelines; it does not authorize unrelated cleanup.

## Alternatives

A dedicated operation phase was rejected because it erases distinct ordinary, restored, history-final and uncertain-effect progress or requires a second hidden phase ledger. Reusing successor-review-required would invent an observed event; evidence-required/blocked would conflate proof loss with effect uncertainty or permanent refusal. Moving listener attachment alone was rejected because it would permit effectful resume during an uncovered interval. Retaining v4 with an optional field was rejected because strict old v4 readers reject new shapes and would not honor the fence. Treating same epoch/hash/revision or a recovered effect receipt as gap continuity was rejected because none proves absence of a missed successor.
