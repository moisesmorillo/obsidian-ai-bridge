# M7.4 design: durable cursor witnesses for bounded inventory

**Status: accepted for isolated local TDD after independent corrective review** investigate-5eb505b68c8fa1e53b3ca98d11123244 (ready for local TDD with bounded test gates). Not yet implemented or Workers Free qualified. Owner authorization covers necessary local design/implementation but not remote qualification, sync activation, deployment, push or a milestone-complete claim. Two earlier draft reviews found gaps; the second rejected a one-shot witness claim because it stranded a scan after a crash before dispatch. ADR 0019 and the authoritative M7 addendum record the retryable-journal correction.

## Invariant and accepted boundary

An R2 LIST cursor is opaque. R2 documents lexicographic *object* order, not unique cursors across pages ([Workers R2 API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/), retrieved 2026-10-02). Existing replay rejects only adjacent equality: an empty-page `A → B → A` can yield a false complete inventory. The accepted M7 spec requires no repeated output cursor, even non-adjacent, same-ID replay after interruption without another LIST if an exact step chunk exists, ≤20,001 pages, at most two LIST attempts per page and 24-hour scan expiry. An initial `null` cursor is **not** a visited output; every truncated output must be nonempty and absent from **all prior truncated outputs**. The current 8,192-byte manifest cannot hold 20,000 SHA-256 digests (640,000 raw bytes). A false-positive filter can reject a valid scan, and reading all earlier chunks on every page would take up to 199,990,000 R2 reads. Use an immutable digest-keyed witness for each truncated output.

## Versioned keys and records

- New scans create only strict **manifest schemaVersion 2** / protocolMajor 1, with a closed `cursorWitnessMode: 1`. Historical v1 manifests remain decodable for tombstone/expired cleanup only: no v1 continuation, complete handle/page, same-ID upgrade or inferred witness. A previously deployed M7.4 v1 scan is not claimed. An exact maximal-field canonical JSON fixture measured **8,550 bytes** for v2: 4,096-byte R2 cursor encoded as 5,462 characters, a 720-byte Markdown lastKey, all 64 maximum-width sequences and capped counters. The same accepted v1 fields already measure 8,528 bytes against an 8,192-byte cap. Set the **v2** manifest cap to 9,216 bytes with worst-case byte tests; preserve the v1 decoder's 8,192-byte cap. Document the changed permanent tombstone maximum in ADR 0018.
- Under one scan's `chunks/` namespace, add `claims/<canonical-step>.json` and `cursors/<64-lowercase-hex-sha256-of-raw-output-cursor>.json`. The protocol key codec, strict record decoders, R2 key classifier and cleanup allowlist must all agree; no raw cursor, note path, content or caller-provided key appears in these records. Reject a digest collision as a divergence, never a complete scan.
- The cursor witness is create-only canonical JSON schemaVersion 1 / protocolMajor 1 binding exact `vaultId`, `inventoryId`, `step`, `chunkHash` and `cursorDigest`. A maximal sample with 36-character IDs, 64-character digests and step 20,000 measures **313 UTF-8 bytes**; enforce a **384-byte** body limit.
- The per-step claim is an **exact-CAS attempt journal**, not a one-shot ban on another PUT. It binds the same chunk/digest/scan/step plus a fresh UUID `claimId` per `attempting` generation and a closed `attempting | retry_wait` state. `retry_wait` stores the conservative retry floor (epoch milliseconds); the binding never changes across generations. Enforce a separately byte-tested **512-byte** cap and strict state-specific fields. A definite prior journal with different chunk/root/digest fails the scan. An exact journal plus an exact witness for this step can be adopted after a lost response, regardless of which isolate wrote it.
- At most T≤20,000 truncated steps yield T stored journals and T stored witnesses: **T × (512+384) ≤17,920,000 body bytes** plus keys/metadata. The accepted 192-MiB chunk-evidence cap is separate. Retain the manifest tombstone permanently, ≤9,216 bytes for v2 or ≤8,192 for v1 per admitted ID plus metadata; no global retained-storage/account quota is established yet. One journal key can have many replaced generations, which change operation counts, not live object counts.

## Authority and recovery sequence

1. Only a strict unexpired v2 manifest and own marker-gated active slot can start/continue. Reserve the original manifest's data-read attempt by exact CAS **before** a LIST/head GET. A fresh invocation shares a counted 400-physical-R2-call budget. On resumed reserved work read the deterministic chunk first and validate exact bytes/root/step/input digest, transcript, count, head schema, key order and output digest. Never relist when an exact chunk exists. The existing two-attempt page cap, chunk create/readback and failure fences remain unchanged.
2. For each verified truncated chunk, read the digest-keyed witness and per-step journal. An earlier-step or conflicting witness proves a cycle/divergence; exact-CAS manifest to `failed` and release only the confirmed failed scan's exact own slot. A matching witness **with a strict journal binding for this step** authorizes the original-generation manifest advance. If either read is unavailable, retain same ID and return `effect_unknown`; an absent journal cannot authorize a stored witness.
3. If both witness and journal are definitely absent, re-observe exact reserved manifest, active slot and unexpired server time, then create-only an `attempting` journal carrying a fresh random UUID. Only a confirmed exact read-back of **its own UUID** authorizes this invocation's one conditional create-only witness PUT. An uncertain journal write is not blindly repeated: same-ID replay reads its exact deterministic key. Two isolates cannot both own the same generation with different UUIDs. If one sees the other's valid generation, it does not send that generation's target PUT.
4. If an `attempting` journal exists but the witness is absent, do **not** assume the previous PUT never dispatched. After the journal object's own uploaded+1,100-ms cooldown, re-observe exact absence and CAS that journal to `retry_wait` with floor `max(observedAt+1,100 ms, target response floor available to this transitioning invocation, previously persisted floor)`. A response still in flight is not yet known and cannot retroactively fence a different isolate's earlier dispatch; the create-only predicate and exact witness fence that overlap. No target PUT in this invocation. When both stored floor and current journal cooldown pass, exact-CAS to a **new** `attempting` UUID, then the winner alone attempts one PUT with the same original create-only predicate and immutable bytes. A rejected/readback-missing target leaves that journal for another exact recovery. An old PUT still in flight can overlap a newer PUT after the floor; R2's atomic create-only predicate and exact-byte validation, not elapsed time, protect against overwrite or false success. Honor any new actual R2 throttle response before attempting another write. No physical per-step or lifetime PUT ceiling is asserted under repeated failure; one target PUT per confirmed own generation per invocation, bounded by the 24-hour expiry and physical 400-call invocation cap.
5. Immediately before claim create, journal CAS and manifest advance, check exact reserved manifest/own active slot and expiry; the journal binding is never silently rebased. `replaceManifest` must preflight the **original reserved** ETag/body, and only a confirmed advance from that same generation may update the cursor and counts. A generation racing expiry may leave a late orphan, but the expired/failed retained manifest and slot fence prohibit completion. An uncertain/refused manifest CAS returns `effect_unknown`, never an optimistic next page. Only a terminal chunk (`truncated: false`, `outputCursor: null`) has no cursor journal/witness. Final vector capture, complete CAS, exact slot release and evidence pages require strict v2; complete manifest authority derives from all prior transitions having been fenced, not schemaVersion alone. Deleting live witness/claim objects is forbidden. Consumers must traverse verified contiguous evidence pages from `cursor: ""` through final marker before asserting absence; a forged later cursor does not prove its earlier pages were consumed.
6. `failed` phase is durable before `inventory_incomplete`; a throttled failure CAS returns same-ID progress with floor and uncertain/refused CAS returns `effect_unknown` retaining the slot. A same-ID continuation/start can release a **confirmed failed** scan's exact active slot. Never return completion after expiry, including an in-flight PUT's late success.

## Closed journal and witness transition table

Every row requires an exact verified reserved chunk, strict original v2 manifest, own active slot and unexpired clock; reread those preconditions before each journal mutation and before each target dispatch. A check immediately before dispatch **is not a lease**: overlapping older and newer conditional PUTs are allowed and are safe only because the immutable body is identical and both writes use `If-None-Match: *`. After the PUT, its response alone never advances the manifest: exact journal/witness/manifest generation evidence is required. `null` initial input is not a visited cursor. No row retries the page's LIST when a valid chunk exists.

| Journal / witness observation | Action and next authority |
| --- | --- |
| Journal absent, witness absent | Create-only `attempting` journal with fresh UUID and exact chunk binding after rechecking manifest/slot; only exact **own UUID** read-back authorizes this invocation's first target PUT. Lost journal-create response requires read-back, not another unclaimed target dispatch. |
| Journal absent, witness present | Divergence; fail scan by exact manifest CAS. A valid witness could not have been written without a confirmed journal generation. |
| Journal `attempting`, witness exact same step/root/digest | Advance the originally reserved manifest by exact CAS. Current journal UUID need not belong to this recovering isolate. |
| Journal `retry_wait`, witness exact same step/root/digest | Advance the originally reserved manifest by exact CAS even before retry floor; a confirmed target effect obviates retry. |
| Journal `attempting`, witness definitely absent; journal cooldown pending | Return same-ID progress with journal `uploaded+1,100 ms` floor; no target PUT. |
| Journal `attempting`, witness definitely absent; cooldown elapsed | CAS same journal to `retry_wait` with monotonic floor at least observation time+1,100 ms and every **known** target floor. If CAS effect unknown, reread the exact journal generation; do not treat another isolate's state as own target-dispatch authority. No target PUT this invocation. |
| Journal `retry_wait`, witness definitely absent; floor or journal cooldown pending | Same-ID progress with maximum safe floor, no PUT. |
| Journal `retry_wait`, witness definitely absent; both floors elapsed | CAS same journal to fresh `attempting` UUID, preserving original chunk/digest binding. Only exact own-new-generation read-back plus current journal/manifest/slot/expiry re-observation permits **one** conditional target PUT in this invocation. A refused CAS or different UUID returns progress/uncertainty, never dispatches. |
| Journal or witness invalid, key/identity/root/digest mismatch, earlier-step digest witness | Exact-CAS manifest to `failed` (confirmed failure required before `inventory_incomplete`/own-slot release); unavailable reads remain `effect_unknown`, and CAS throttle defers. A matching claim UUID from another isolate is not a mismatch. |
| Journal/witness matching but original reserved manifest CAS refused or response lost | Reread the **original expected successor** or original unchanged generation. Do not refresh to CAS from a newer manifest. Return same-ID progress only on confirmed exact successor; otherwise `effect_unknown`. Never issue a handle from an uncertain response. |

All conditional journal PUTs preflight observed ETag/body/uploaded and reserve their read-back. Journal create, `attempting→retry_wait`, and `retry_wait→attempting` each have independent same-key cooldown checks. A dispatcher must honor its locally known target throttle/uncertainty floor and every persisted floor before its next PUT, carrying a response floor into its next eligible `retry_wait` CAS; an uncertain floor CAS is never target-dispatch authority. A separate isolate cannot observe a response floor that has not yet been persisted. Neither a late response nor a still-in-flight PUT retroactively prohibits a previously dispatched new-generation PUT: exact create-only bytes, not a timing lease, prevent false success. Test floors reported after the journal upload cooldown and verify that the recovery observation floor dominates or preserves every floor visible to that invocation. This owner-confirmed interpretation applies only to isolated inventory witnesses; mutation attempt floors retain their separate accepted contract. An in-flight PUT whose response never arrives has no provably finite completion time; the original create-only predicate, exact-byte check and expiry fence—not the 1,100-ms delay—provide safety. A digest collision is detected because the existing witness points to an earlier step or conflicts with the immutable chunk for the same step; it is never adopted as a match to a different raw cursor.

## Cleanup and conservative capacity

Scoped cleanup checks the exact expired manifest tombstone, own-slot-release proof and canonical chunk/claim/witness keys under its own `chunks/` prefix. Delete at most one scratch key per invocation by counted DELETE plus counted absence read-back; **never delete the manifest**. R2 DELETE is unconditional; an empty prefix LIST proves no object *then*, not that a delayed PUT can never appear. A later cleanup pass can reclaim such an orphan; `retained` is not a complete-sync or perpetual-reclamation witness. Unknown/foreign/malformed keys fail closed. At most P≤20,001 chunk objects plus 2T≤40,000 journal/witness objects = **N≤60,001** scratch objects per maximal scan. A no-retry cleanup envelope of about 2N manifest/slot GETs + N LISTs + N DELETEs + N absence GETs + final observations is **5N+3≤300,008 R2 calls** over ≥N+1 invocations; retries, races and late writes add attempts, so this is *not* a lifetime bound.

For first-success scanning: ≤2P+2H=**60,002** LIST/head GETs (H≤10,000); up to **10T=200,000** first-attempt witness/journal calls (witness GET, journal GET, two manifest/slot observations, journal create GET+PUT+readback, witness create GET+PUT+readback), plus an **illustrative**, not proven, 12P=240,012 other control/chunk/final-vector calls, total illustrative **500,014**. An attempt recovery adds journal GET, witness GET, exact-CAS to retry_wait (≤3 calls), exact-CAS to new attempting (≤3), and conditional witness create (≤3) across **different invocations** and known floors. An analytical first pass at the **pre-dispatch per-invocation reservation** follows; it is not verified until physical-call traces exercise every branch. The current one-key adapter takes at most 1 GET for a strict read, or preflight GET + conditional PUT + read-back GET = 3 dispatched calls for each attempted create/CAS, including unsuccessful/throttled paths (which usually dispatch fewer). Current runner admission reserves 6, captures 64 heads at ≤2 GET each plus 2 for progress CAS, finalizes with ≤128 head reads+3 manifest-CAS calls; current evidence pages reserve 2 GET+16 chunks, cleanup reserves 8. New per-step happy path with existing chunk: chunk GET1 + witness GET1 + journal GET1 + manifest/slot re-observe 2 + journal create3 + pre-target journal/manifest/slot GET3 + witness create3 + manifest advance3 = **17**; allow at least **32 reserved step credits** for additional exact proof reads, divergent-failure CAS and retry-wait CAS branches (never two journal CAS writes to the same key without a cooldown). Fresh LIST path remains ≤12 inside the step. This proposed 32 must be replaced or proved by branch-specific counted tests before implementation is accepted.

| Invocation path | Proposed reserved physical-call ceiling before dispatch; prove by counted tests |
| --- | --- |
| Start/admission and 64-lane capture | 6 initial + 130 lane/progress = **136** in one start invocation; often split across several starts. |
| Continue first or replayed page | 2 manifest admission + 1 slot + **32** step = **35**, including up to one LIST/head GET when no verified chunk, one journal state transition or own journal create, witness create and read-backs. Branches requiring more credits must return same-ID progress **before** dispatch. |
| Complete/final vector and release | 2 manifest +1 slot+131 capture/progress = **134**; release separately reserves up to 3 additional calls. |
| Evidence page | 2 authority GET + up to 16 chunk GET = **18**. |
| Scoped expired cleanup | Manifest GET1+slot GET1+slot CAS up to3, **or** LIST1+DELETE1+read-back1: ≤5 actual, existing **8** reserved. |

All are below **400 actual R2 calls per invocation**, but the counted adapter (not this table) must enforce the cap. Every branch must reserve its own worst-case before the read/write it proposes. Test unknown/refusal/late read-back and preflight exhaustion against counted raw R2 calls, not just helper invocations. Number of invocations under repeated infrastructure uncertainty is not finitely bounded; after expiry no new PUT or complete handle is authorized. R2 operations per scan and cleanup could consume a large fraction of a Free month; permanent tombstones accumulate until an explicit admission/account quota is designed.

Cloudflare primary sources checked 2026-10-02: [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) list Free **100,000 incoming requests/day**, **10-ms CPU per HTTP request**, 50 ordinary subrequests/request and **1,000 internal-service subrequests/request**; [R2 pricing](https://developers.cloudflare.com/r2/pricing/) lists 1 million Class A/month and 10 GB-month Standard storage on Free. A maximal scan plus cleanup may take >100,000 invocations when retries/deferrals are included; neither a same-day completion nor bounded global storage is claimed. A 400-call cap is less than 1,000 internal subrequests but **does not prove** Free CPU, R2 billing or account admission. Local workerd measurements plus separately authorized isolated Workers Free qualification of worst paths are required before activation/M7 COMPLETE; no remote qualification is authorized by this document.

## Red/green and independent review gates

- Strict v1 starting/scanning/complete manifest refusal; v2 maximal-byte fixture, historical v1 8,192 cap. No repair/inferred witness.
- Empty and headed `A→B→A`, longer cycles and SHA-256 collision/mismatch; initial null cursor is not visited; neither replay nor finalize produces an unfenced handle. Per-page and final evidence checks cannot delete live witnesses.
- Crash before journal claim, during unknown claim PUT, **after confirmed claim but before witness dispatch**, after witness PUT before readback, after witness confirmation before manifest CAS, after lost CAS; two isolates race different claim UUIDs; exact same-ID recovery and no third LIST.
- Retry_wait CAS refused/throttled/unknown, target PUT refused/throttled/unknown, old in-flight target PUT racing new generation; no overwrite, no false completion, no write from a losing isolate, observe known floor. Expiry during chunk/journal/witness writes and delayed orphan after empty-prefix cleanup observation.
- Strict maximal 512-byte journal/384-byte witness codec, key and cleanup allowlist; physical R2 call accounting across all paths and ≤400-call preflight. Workerd proves conditional create/CAS semantics; synthetic maximal profile measures actual CPU/memory independently from Workers Free gate.
- M7 spec and successor ADR 0019 now authorize local TDD only; their acceptance does not prove implementation. Prior review's authority, causal-fence, v1 compatibility and expiry/cleanup design findings are closed as contracts, **not tested implementation**. Counted worst-branch paths, local workerd composition and Free-tier/resource qualification remain open. No push, sync activation, remote deployment or M7 completion claim follows from this design.
